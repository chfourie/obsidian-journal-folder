## Project

Obsidian community plugin (`id: journal-folder`) that adds folder-based journaling utilities. Any folder in a vault can act as a journal — notes named `YYYY-MM-DD`, `gggg-[W]ww`, `YYYY-MM`, or `YYYY` are recognized as daily/weekly/monthly/yearly entries. Quarterly notes (`YYYY-Q[1-4]`) are an **opt-in** fifth tier gated by the `quartersEnabled` setting; they slot between yearly and monthly when on. The vault root is *not* supported as a journal folder due to Obsidian link-resolution behavior.

The plugin is built with TypeScript + Svelte 5 (runes API, `$props`, `$state`, `$derived`) and bundled with esbuild into a single `main.js`.

## Commands

```bash
npm run dev        # esbuild in watch mode → main.js (inline sourcemap)
npm run build      # tsc --noEmit type check, then production esbuild
npm test           # Vitest run (one-shot)
npm run test:watch # Vitest in watch mode
npm run lint       # eslint-plugin-obsidianmd — the Obsidian community-review ruleset
npm run lint:fix   # same, auto-fixing what's safe
npm run version    # bump manifest.json + versions.json from package.json version
```

Tests live in `tests/` and mirror the `src/` layout. **Linting uses `eslint-plugin-obsidianmd`** (flat config in `eslint.config.mjs`) — the *same* ruleset the Obsidian community-review scanner runs against a submitted release, so `npm run lint` reproduces those findings locally. It type-checks against `tsconfig.json` (scoped to `src`; tests are excluded from the tsconfig). Run it before tagging a release to avoid surprises in the published review. Prettier config also exists and is run manually if desired.

## Architecture

### Plugin shell → feature set

Entry point is `src/plugin/journal-folder-plugin.ts`. It instantiates a `PluginFeatureSet` and registers its features in order:

- `JournalFolderSettingsFeature` — owns the global settings, persists them via `plugin.saveData`/`loadData`, registers the settings tab, propagates settings to the other features, and applies global side-effects (`applyStartOfWeek`, the body class for *Hide journal-folder.md in file explorer*). Its `saveSettings` is `public readonly` so the sidebar feature can mutate global settings (e.g. *Set as default*) through the same pipeline.
- `JournalHeaderFeature` — registers the `journal-header` markdown code block processor that mounts the in-note header + calendar.
- `JournalTasksFeature` — registers the `journal-tasks` markdown code block processor and owns a shared `TaskCache` that the sidebar's task panel also consumes. See the *Tasks* subsection below and [docs/tasks-design.md](docs/tasks-design.md).
- `JournalSignifiersFeature` — renders **signifiers** (tag → icon) in reading view (`processSignifiers` markdown post-processor) and live preview (`signifierLivePreviewExtension`, always on in Live Preview but **inert in Source mode** — it gates on Obsidian's `editorLivePreviewField` and emits no decorations there, so raw markdown editing shows the tag text and no gutter icons), and registers the *Modify signifiers on current line…* command + editor-menu item. Placement is the global `signifierPlacement` setting with two values, both left-margin gutters (`.jf-signifier-gutter` absolutely positioned against the entry's content host / line `.jf-signifier-host`, vertically centred via `top:0; bottom:auto; height:1lh`): `margin` hangs the icon just left of **each** entry (indented with nesting); `margin-column` (the **default**, carries `.jf-signifier-column`) aligns **every** icon in one far-left column (physical-journal left rule). The matched tag text is hidden in reading view when `signifierHideTagInReadingView` (on by default, via the `.jf-signifier-hidden-tag` class) and in live preview when `signifierHideTagInLivePreview` (on by default, via a `Decoration.replace` over the tag token — revealed for editing per the pure `computeTagHideRanges`: `signifierShowTagsOnActiveLine` (off by default) reveals **all** tags on the cursor's line, off reveals only the tag the selection touches; the decoration set rebuilds on `selectionSet` only when tag-hiding is on). Reading view also splits a soft-break paragraph/heading (one `<p>` with `<br>`s, *Strict line breaks* off) into per-line `.jf-signifier-line` wrappers so each line gets its own gutter marker instead of all clumping at the block start; list items are left intact (each `<li>` is already one entry). The **horizontal** position of both gutters is set by **measurement, not theme-specific CSS** — a fixed CSS offset collides with themes/snippets that restyle bullets/checkboxes/indentation. Reading view: `gutter-positioner.ts` batches all `getBoundingClientRect` reads then all `left` writes in one `requestAnimationFrame` (one reflow). Editing view: the live-preview `ViewPlugin` uses CodeMirror's `coordsAtPos` inside a batched `view.requestMeasure` on `docChanged/viewportChanged/geometryChanged/placementChanged`. The offset is scroll-invariant (marker + reference move together) so there is **no scroll recompute**; markers are `visibility:hidden` until the first measurement reveals them (`.jf-positioned`, no wrong-x flash). Recompute triggers (both placements): after the post-processor, on `css-change` (theme metrics), on `active-leaf-change`/`layout-change`/`file-open` (Obsidian can restore a cached preview without re-running the post-processor), and — crucially — via a **`ResizeObserver` on each `.markdown-preview-sizer`** (observing the *border box*, so our own padding can't loop it) which fires on the sizer-width changes that carry no catchable workspace event (readable-line-width toggle, window resize, sidebar toggle). The `signifierReserveGutter` toggle (global-only, **on by default**) reserves a left lane on the content container's `padding-inline-start` equal to the **deficit** by which the leftmost icon would clip past the pane's nearest overflow-clipping ancestor (NOT the centered sizer) — 0 when the existing margin already fits — so icons never clip with readable line width off / narrow views. The current reserve is read back from the live inline padding (not a `WeakMap`, which desynced on navigate-back) so it can't oscillate, and the base padding is `WeakMap`-cached so it never compounds. Signifiers apply to any rendered markdown, not just tasks, and have their **own settings tab**. Signifiers and task categories are **global-only** (in `GLOBAL_ONLY_FIELDS`, never per-folder or per-flow); task categories live under the Tasks tab. A category may carry an optional **range cap** (`TaskCategory.maxRange`) that bounds how far its tasks reach in the aggregated lists (sidebar + in-note block), measured the same way the range is — smallest cap wins, a larger list range is clamped to it, `all` always clamps; enforced by `task-range-cap.ts`'s `makeRangeCapFilter` during collection. **Anchor is a genuine date range** (`anchorRange`): `today` → a single day; `note` → the active note's whole period. The range setting and each cap are applied via `expandRange(anchor, unit)`, which snaps the anchor span's endpoints out to the unit's calendar boundaries — this is the materialised union of `periodAround` over every day in the span (contiguous windows → outer envelope, no loop). It replaces the older "floor the unit up to the note's tier" logic, which broke when tier boundaries didn't line up (e.g. month vs week). So a `day` range/cap on a monthly note still resolves to the whole month, but a `week` range on a monthly note correctly includes the partial-week spillover at each end. See [docs/signifiers.md](docs/signifiers.md).
- `JournalAutoTemplateFeature` — listens to `vault.on('create')` (after `workspace.onLayoutReady`) and seeds new journal notes with a template body when the global/folder `auto-template-enabled` setting is on. Templates are **notes with standardized filenames** (`daily-template.md`/`weekly-template.md`/`monthly-template.md`/`quarterly-template.md`/`yearly-template.md`, plus `default-template.md` fallback), copied verbatim (front matter included). They live in the global `templateFolder` (default `Templates/journal-folder`) and, taking precedence, in a `<journalFolder>/<templateOverrideFolderName>/` subfolder (default `Templates`). Resolution precedence (first non-empty): override `<tier>-template.md` → override `default-template.md` → legacy `journal-folder.md` body (front-matter stripped, still honoured) → global `<tier>-template.md` → global `default-template.md` → built-in `DEFAULT_AUTO_TEMPLATE`. A standardized template note **previews as the current period's entry** — `JournalHeaderFeature.resolveHeaderNote` detects it (`templateFileTier`) and builds a synthetic current-period `JournalNote` (`buildTemplatePreviewNote`), so editing `monthly-template.md` renders as this month's note (signifiers included; nav links best-effort/inert for global-folder previews). A one-time migration (`maybeMigrateInlineTemplates`, gated by `templatesMigratedToFiles`) moves the legacy inline `data.json` template fields into files (config-note bodies and the old field values are left as backups). `templateFolder` / `templateOverrideFolderName` / `templatesMigratedToFiles` are **global-only**; the pure helpers live in `src/data-access/template-folder.ts`. See [docs/auto-template.md](docs/auto-template.md).
- `JournalFolderSidebarFeature` — registers the `journal-folder-sidebar` view type and the calendar ribbon icon. The sidebar is the entry point for folder selection, the calendar, the inline configuration editor, the *Initialise a new journal folder* action, and (when `tasksSidebarEnabled` is on) the task panel that shares `JournalTasksFeature`'s cache. See [docs/sidebar.md](docs/sidebar.md).

`PluginFeatureSet` (`src/plugin/plugin-feature-set.ts`) is a tiny lifecycle multiplexer: `load`, `unload`, `useSettings`, and `onExternalSettingsChange` fan out to every registered feature with try/catch around each. Adding a new feature = create a `PluginFeature` subclass and `addFeature(...)` it in the plugin constructor.

### Settings resolution

All features extend `PluginFeature` and resolve settings through three layers (later overrides earlier): global settings → folder front-matter (`journal-folder.md` in the same folder as the file) → embedded `key: value` config in the current `journal-header` code block. To add a configurable behavior, add the field to `JournalFolderSettings` + `DEFAULT_SETTINGS` in `src/data-access/journal-folder-settings.type.ts` — the resolver picks it up automatically.

Global-only fields (`startOfWeek`, `defaultJournalFolder`, `hideJournalFolderNotes`, `sidebarMode`, and every `tasksSidebar*` / `task*` field) are intentionally not honoured at the folder/embedded layers — see the per-field JSDoc for the rationale (locale singletons, UI preferences, task model is process-wide, etc.). **Exception:** `taskMigrationPlacement` and `taskMigrationHeading` *are* folder-honoured (a per-note layout concern, not a process-wide model/UI preference), so they appear in `PER_FOLDER_FIELDS` despite the `task*` prefix.

`PER_FOLDER_FIELDS` in `src/features/journal-folder-sidebar/folder-config-sync.ts` is the canonical list of fields the per-folder modal lets users edit; it's typed as `const satisfies ReadonlyArray<keyof JournalFolderSettings>` so the type system catches drift if a new field is added without an entry. `kebabCase` (in `data-access/string-utils.ts`) is the inverse of the existing `camelCase` and is used when writing per-folder overrides to YAML front matter.

See [docs/settings-resolution.md](docs/settings-resolution.md) for the per-folder lookup nuance and key-case conversion rules.

### Journal note model

`src/data-access/journal-note.ts` picks one of up to five `JournalNoteStrategy` records (daily/weekly/monthly/quarterly/yearly — quarterly only when `settings.quartersEnabled` is truthy) by regex-matching a `TFile`'s basename, then exposes navigation methods (`forwardInTime`, `backInTime`, `closestSibling`, `getHigherOrderNotes`, `getLowerOrderNotes`, `getNotesInPeriod`, `dailyNoteToday`), state predicates (`isPresentTime`, `isPast`, `isExistingNote`, `isToday`), and `hasUnit(unit)` for callers that need to know whether a tier is currently active. **All date math goes through the typed `moment` wrapper in `src/data-access/moment.ts`** (re-exported from `src/data-access`) — `import { moment } from 'src/data-access'` (or a relative `data-access` path), never from `'obsidian'` or `'moment'` directly. The wrapper re-casts Obsidian's `moment` export to its real callable type (`typeof import('moment')`); the raw obsidian export is typed as a non-callable namespace under this project's `esModuleInterop`, which is why direct calls used to need scattered `@ts-ignore`s and tripped the type-checked `no-unsafe-*` lint rules.

`isJournalFileBasename(basename, quartersEnabled)` is exported separately for callers that want the regex check without instantiating a `JournalNote` (the auto-template feature, the journal-header code block processor's "render nothing in non-journal notes" guard, and the sidebar's dynamic-mode active-leaf filter).

See [docs/journal-note.md](docs/journal-note.md) for strategy fields, *medium* title-pattern semantics, and weekly-pattern caveats (`gggg` vs `YYYY`).

### Journal-folder detection

`src/data-access/journal-folder-detection.ts` exports `FOLDER_CONFIG_FILENAME` (`'journal-folder.md'`), `findJournalFolderPaths(app)` (sorted parent paths of every config note in the vault, vault root reported as `'/'`), `isJournalFolder(app, folderPath)`, and `configPathFor(folderPath)`. Single source of truth — the auto-template feature, the sidebar's folder picker, and the *Initialize a new journal folder* candidate filter all import from here.

### UI rendering (Svelte 5)

`JournalHeaderFeature` registers a `journal-header` code block processor that resolves settings, builds a `JournalNote`, builds a plain `JournalHeaderInfo`, and mounts `JournalHeader` via Svelte 5's `mount` API. The primary row shows `back ‹‹ More... · Today · ›› forward`; everything else lives in the More popover, which is **portaled to `<body>`** to escape CodeMirror live-preview widget clipping. The note it renders for is chosen by `resolveHeaderNote`: a real journal note renders for itself; a **standardized template note** (`monthly-template.md` etc. in a template folder) renders for a synthetic *current-period* note of its tier (so the template previews as a live entry); anywhere else (e.g. a `journal-header` block in `journal-folder.md` itself or a non-journal note) it's a no-op. Errors render via `ErrorMessage.svelte` rather than throwing.

See [docs/header-ui.md](docs/header-ui.md) for the popover positioning logic, the delegated `findInternalLinkHref` click handler (necessary because Obsidian's `.internal-link` interception doesn't fire on portaled content), and the secondary-list date-pattern derivation in `secondaryTitlePatternFor`.

### Calendar picker

`JournalCalendar.svelte` (in-note) and `SidebarCalendar.svelte` (sidebar) share the same `buildCalendarInfo` model + `calendarCellClasses` cell-class computation, the same set of `journal-folder-calendar-*` CSS classes, and the same controls strip (year/month picker + *Current* + *Note month* links). The in-note one supports multi-month (1–5 months chosen by `pickVisibleMonthCount` from a ResizeObserver-measured width) and lives in markdown-rendered scope; the sidebar one is always single-month and lives in an `ItemView` so it intercepts every cell click explicitly and routes through `app.workspace.openLinkText` (Obsidian's `internal-link` delegation only fires inside markdown containers).

The picker trigger label is the literal **Year/Month** in both calendars; the actual `MMM YYYY` value appears in the linked title row above each month grid (which doubles as a click target for the month, year, and quarter notes). *Current* jumps to today's month; *Note month* jumps to the host note's month (in-note) or the active journal note's month (sidebar). Show/hide gates live in `calendar-navigation.ts` — `shouldShowCurrentLink(visible, today)` and `shouldShowNoteMonthLink(visible, noteMonth, today)` — both pure and unit-tested.

See [docs/calendar.md](docs/calendar.md) for the deep details: month-window placement and `pickVisibleMonthCount` constants, fixed-width day cells, the dedicated divider grid track, cell-class stamping (and why we don't trust Obsidian's link-resolution pass), the date-picker popover behaviour, the desktop/mobile spacing split, and the platform-specific visibility defaults.

### Tasks

`JournalTasksFeature` registers a `journal-tasks` markdown code-block processor and owns the `TaskCache` that both surfaces share. A task is any line matching `/^(\s*[-*+]\s+)\[(.)\]\s?(.*)$/` whose status character is recognised by the active `TaskModel` — `simpleTaskModel` (`[ ]` / `[x]`) or `bulletJournalTaskModel` (`[ ] [/] [x] [>] [-]`). Resolution goes through `resolveTaskModel(settings)`; the `TaskModel` interface is the strategy seam for a future Tasks-plugin model.

Filtering goes through `buildReferenceRange`. Each sidebar panel's reference is two orthogonal axes set in its scope panel (`TaskScopePanel.svelte`): an **anchor** (`today` or `note`) and a **range** (`day` / `week` / `month` / `quarter` / `year` / `all`). The range is the calendar period of that size *containing* the anchor (`periodAround(base, unit)`); `note` anchors on the active journal note's date (falls back to today on a non-journal leaf); `all` applies no date filter (`allTimeRange`, a window so wide every note intersects it). `quarter` is only offered when `quartersEnabled`. In-note blocks ignore the axes and always follow the host's own tier range (or `[today, today]` for non-journal hosts). Folder scope is fully independent (`resolveTaskFolders`): **Current note's folder** / **All journal folders** / a single **specific folder**. `findTaskCandidates` walks the resolved folder(s) and keeps files whose `JournalNote` range intersects the reference range. The task panel header shows a one-line read-only summary (`anchor · range · folders · filter`) and a **Scope ▾** opener on the right that toggles the panel. `sortTasks` orders ascending by source-note range length so daily tasks always appear first. Status mutations go through `task-transition.ts` which uses `vault.process` with a line-match guard — a stale cache aborts with a `Notice` rather than blind-writing. Left-click cycles to `model.nextStatus`; right-click / long-press (and left-click on a **self-cycling** status, i.e. one whose `next` is its own id — `model.opensPickerOnClick(id)`) opens the in-house `openStatusPicker` panel (`status-picker-panel.ts`) — a `<body>`-portaled status list, **not** a native `Menu`. That panel is shared by all four checkbox surfaces (sidebar panel, in-note block, reading-view post-processor, live-preview extension); each passes its own writer to `onSelect` (disk `setTaskStatus` everywhere except live preview, which writes through the open editor). The panel also grows a **"Migrate task…"** row when the task is migratable: capability comes from a module-level provider the feature registers once (`setStatusPickerMigrationProvider` → `buildSingleTaskMigration`, resolved per file so folder overrides apply — returns `null` for done tasks / non-journal notes / flows with no migrated status), and each surface passes the task's current `rawText` (omitting it suppresses the row). The native `Menu` survives only in the `editor-menu` integration (`appendStatusMenuItems`), which legitimately extends Obsidian's own editor context menu. The status editor's *Next status* dropdown flags the self-id option as "(show picker — don't cycle)". View-local `showCompleted` toggling in the in-note block does not persist; the sidebar's identically-named toggle does. **Task migration** (`task-migration.ts` + `task-migration-menu.ts`) moves active tasks between notes *within one folder*: it stamps the origin with the flow's `migratedStatus` (a per-flow id constrained to an inactive status, surfaced as `model.migratedStatusId`), appends a forward reference, and writes top-level copies (each carrying a back-reference to its origin) into the destination at the position set by the folder-honoured `taskMigrationPlacement` / `taskMigrationHeading` settings (`computeInsertion`). Each reference direction can be disabled (`taskMigrationAddToReference` / `taskMigrationAddFromReference`); when enabled, the markers are global-only and driven by a style (`taskMigrationReferenceStyle` text/emoji/lucide → editable `taskMigrationToMarker` / `taskMigrationFromMarker`; default style `lucide` with `lucide:redo-dot`/`lucide:undo-dot`; emoji/lucide modes add `EmojiPickerModal` / `LucidePickerModal`). Lucide markers are stored as `lucide:<name>` tokens and rendered as icons in reading view by the `processMigrationReferences` post-processor, which also fades each reference (marker + link) to `taskMigrationReferenceOpacity` (default 30%, full on hover via `.jf-migration-ref`). The editing-view counterpart is `migrationReferenceLivePreviewExtension` (`migration-reference-live-preview.ts`): a CodeMirror `ViewPlugin` that replaces each `lucide:<name>` marker with its icon in **Live Preview** (revealed back to raw text while the selection touches it), and is **inert in Source mode** (gated on `editorLivePreviewField`) so raw editing shows the literal token. Only `lucide:` markers are substituted (text/emoji markers read fine as literal chars); `findLucideMarkerSpans` (pure) locates a standalone `lucide:` token preceding a `[[wikilink]]`. The plugin's own task lists strip the reference from display text (`stripMigrationReferences`, markers fed via `TaskCache.setMigrationMarkers`) so raw `lucide:` tokens never surface there. Three menu triggers: a per-task `editor-menu` item, and two `file-menu` items (*from this note* / *to this note*) that open the grouped multi-select `MigrationTaskPicker` (opt-in — nothing selected by default). Origins are stamped before copies are written, so a drifted line is skipped rather than duplicated. See [docs/tasks-design.md](docs/tasks-design.md).

### Sidebar

`JournalFolderSidebarFeature` registers a view of type `journal-folder-sidebar` plus a `calendar-days` ribbon icon. The view (`JournalFolderSidebarView extends ItemView`) mounts `JournalFolderSidebar.svelte` and exposes a `SidebarUpdateApi` (`setSettings`, `setKnownFolders`, `setActiveFile`, `setSelected`, `bumpVault`) that the component registers at mount; the view pushes settings updates and active-leaf snapshots into the component's reactive `$state` without re-mounting. `bumpVault` is fired on every vault `create`/`delete`/`rename` so the synthetic anchor `JournalNote` (built once from a duck-typed TFile via `buildAnchorNote`) rebuilds — its `noteNames` snapshot would otherwise go stale on file mutations.

The header reads **JOURNAL FOLDER (Dynamic)** / **(Static)** with the bracketed mode tag in `var(--text-accent)`. A single **More...** link to the right of the header opens `SidebarMenuPanel.svelte` — a `<body>`-portaled styled panel (matching the task scope panel) carrying every secondary action: mode toggle, *Switch to default folder* (conditional), *Set as default folder* (conditional), *Edit folder configuration* (conditional), *Initialise a new journal folder*, and *Re-populate note from template* (conditional — only when the active file is a journal note in a templating-enabled folder, gated by `ActiveFileSnapshot.repopulatable` computed in the view via `isTemplateableNote` + resolved `autoTemplateEnabled`). The re-populate action overwrites the note with its resolved template (`resolveNoteTemplate`, shared with the auto-template create listener) after a destructive `confirmModal` (`src/ui/confirm-modal.ts`, `mod-warning` button). Items come from `buildMenuItems()` (resolved lazily on open) as `SidebarMenuItem[]`; each row renders its Lucide icon via Obsidian's `setIcon`. The folder picker beneath the header still opens an Obsidian-native `Menu` (via the `showMenu` prop → `showMoreMenu`); only the More... menu moved to the styled panel.

**Dynamic mode** subscribes to `workspace.on('active-leaf-change')`; when the active file is a recognised journal note in a known journal folder, the sidebar's selected folder switches to the file's parent and the calendar scrolls to that note's period. **Static mode** ignores active-leaf events. Both are persisted as the global `sidebarMode` setting; the user toggles via the More... menu.

The *Initialise a new journal folder* action opens a `FuzzySuggestModal<TFolder>` listing every folder that isn't already a journal folder (root excluded). Picking a folder creates `journal-folder.md` seeded with `journal-folder-title: <folder name>` and switches the sidebar to the new folder.

The *Edit folder configuration* action opens `FolderConfigModal`, which reuses the settings tab's `renderSettingsForm({ ..., mode: 'folder' })` entrypoint with global-only sections suppressed. Saves diff against the current global settings via `computeFrontMatterDiff` (in `folder-config-sync.ts`) and apply through `app.fileManager.processFrontMatter` — fields matching the global config are *removed* from front matter so future global edits flow through, and diverging fields are written as kebab-cased keys. The modal applies Obsidian's `mod-settings` class to `modalEl` and `vertical-tab-content` to `contentEl` so it inherits the plugin-settings dialog's wide skin instead of the default narrow Modal width; the (always-empty) tab-list sidebar that `mod-settings` would render is hidden via CSS on `.journal-folder-config-modal-wrap`.

The *Hide journal-folder.md in file explorer* setting (in the global settings tab) toggles a `journal-folder-hide-config-notes` body class; a CSS rule with `:has(> .nav-file-title[data-path$="/journal-folder.md"])` hides the matching `.nav-file` rows declaratively (no `MutationObserver`).

### Folder layout

```
src/
  plugin/         # plugin entry + feature lifecycle multiplexer
  data-access/    # settings types, FolderSettingsResolver, JournalNote, journal-folder
                  # detection, string utils, PluginFeature base
  features/       # one folder per feature; each owns its *-feature.ts and any
                  # Svelte components / pure helpers
    journal-folder-settings/   # settings tab + reusable settings-form renderer
                               #   (used by both the global tab and the per-folder modal)
    journal-header/            # in-note header + calendar
    journal-auto-template/     # vault-create listener that seeds new journal notes
    journal-folder-sidebar/    # sidebar view, picker, calendar embed, init modal,
                               #   folder-config modal
    journal-tasks/             # journal-tasks code block, task panel components,
                               #   task models (simple, bullet-journal), cache,
                               #   reference range, scope, sorting, transitions
  ui/             # shared Svelte components (NoteLink, ErrorMessage)
docs/             # architecture deep-dives, screenshots, demo vault, developer notes
```

Within `data-access`, every module is re-exported from `index.ts`; features import from `'src/data-access'` (path alias via `tsconfig` `baseUrl: '.'`) or relative paths. esbuild bundles `.svelte` files via `esbuild-svelte` with `css: 'injected'`; `styles.css` is the only CSS shipped separately (Obsidian loads it alongside `main.js`).

## Release

Releases are driven by git tags. `.github/workflows/release.yml` runs `npm run build` on tag push and creates a draft GitHub release with `main.js`, `manifest.json`, and `styles.css` attached. Use `npm version <patch|minor|major>` — the `version` script syncs `manifest.json` + `versions.json` and stages them automatically.

**Preferred path: `npm run release -- <patch|minor|major>`** (`scripts/release.mjs`) runs the whole local pipeline in order, halting on the first failure: preconditions (clean tree + `## [<next>]` CHANGELOG section) → lint → unit tests → build → **E2E** (`node tests/e2e/run.mjs`) → `npm run screenshots` → commit generated docs → `npm version` → `npm run deploy` → commit the demo-vault bump → confirm → push branch + tag. It requires a **local, running, visible Obsidian** (the E2E + screenshot steps drive the real app via the CLI, so it can't run on CI) and the tag push creates the usual **draft** release to review + publish. Flags: `--dry-run` (validate + print plan, change nothing), `--yes` (skip the pre-push confirm), `--skip-screenshots`. Full detail in [docs/agent-notes.md](docs/agent-notes.md) (*Release flow*).

The old **release verification report** (a committed `docs/test-reports/` gallery regenerated each release) was **removed entirely** — regenerating ~74 PNGs every release piled fresh binary blobs into git history and ballooned the repo. The report-generation machinery (`--report` mode, `report.mjs`, `reporter.mjs`, the `test:e2e:report` script) is gone; the E2E suite now only verifies, it captures nothing. Specs still carry their `ctx.step('…')` / `ctx.shot('…')` annotations, retained as **no-ops** in `tests/e2e/lib/harness.mjs` (they document each scenario's intent and cost nothing). The README's own screenshots (`docs/screenshots/`, via `npm run screenshots`) are unaffected and still committed.

After a code change always also build and deploy the artifacts. `npm run deploy` (= `npm run build` + `scripts/deploy-plugin.mjs`) copies `main.js`, `styles.css`, `manifest.json` into the demo vault **and** every plugin folder listed in the git-ignored `deploy-targets.json` (template: `deploy-targets.example.json`); `npm run push` redeploys the current build without rebuilding. The script creates each target folder if missing, writes a `.hotreload` marker (so vaults running the Hot-Reload plugin pick the build up automatically — otherwise reload the plugin once), and **refuses to write through a symlink** so it can't dump files back into the repo. It never copies `data.json`, so each vault keeps its own settings. The demo-vault `main.js` is gitignored; the others are tracked.

### Inspecting / screenshotting via the Obsidian CLI

Obsidian ships a CLI ([help](https://obsidian.md/help/cli)) — `obsidian [vault=<name>] <command>` — that is the preferred way to inspect the live note DOM/geometry and capture README screenshots from real Obsidian instead of guessing. Requires Obsidian **1.12.7+** with **Settings → General → "Command line interface"** enabled and the app running (check `which obsidian` first). Key commands: `dev:dom selector=<css>` (query live DOM), `eval code=<js>` (run JS — `getBoundingClientRect`/`getComputedStyle` for layout debugging), `dev:screenshot path=<file>` (README shots), `command id=<id>` / `commands` (run/list commands), `plugin:reload id=journal-folder` (reload after `npm run push`), `read`/`open`/`create`. Typical loop: `npm run push` → `obsidian plugin:reload id=journal-folder` → `obsidian dev:dom`/`eval` to verify → `obsidian dev:screenshot`.

## Conventions worth honoring

- Prettier: single quotes, 2-space indent, no semicolons, trailing commas `es5`, 80-col print width.
- License headers: every `.ts`/`.svelte` source file starts with the GPL-3.0 boilerplate. Match the existing style when adding new files.
- Date formatting always goes through the typed moment wrapper (`import { moment } from 'src/data-access'`, backed by `src/data-access/moment.ts`) — never `'obsidian'` or `'moment'` directly. It's still the same bundled instance, just typed callable.
- Obsidian-global DOM access uses `activeDocument` / `activeWindow` (not bare `document` / `window`) for popout-window compatibility — the `obsidianmd/prefer-active-doc` lint rule enforces this. `tests/setup-globals.ts` polyfills both to the jsdom document/window so unit tests still run.
- The settings tab (`journal-folder-settings-tab.ts`) is explicitly marked as throwaway code in a comment — don't be surprised by its shape. The `renderSettingsForm` entrypoint is used by both the global settings tab and the per-folder `FolderConfigModal`; a `mode: 'global' | 'folder'` flag drives which sections render.
- When constructing a synthetic `TFile` (e.g. for the sidebar's anchor note), use a duck-typed plain object cast `as unknown as TFile` rather than `new TFile()` — Obsidian's real `TFile` constructor wires `path` through an internal `setPath` that crashes on post-construction assignment.
- Inline action affordances in the sidebar use `<span role="button" tabindex="0">` rather than `<button>` because Obsidian's button styling adds chrome (border/shadow/padding) that can't be cleanly overridden. Always pair with an `onkeydown` handler for Enter/Space activation.
- Always write tests when adding functionality. Pure helpers go under `tests/data-access/` or `tests/features/`; mock surface for Obsidian APIs lives in `tests/mocks/obsidian.ts`.
